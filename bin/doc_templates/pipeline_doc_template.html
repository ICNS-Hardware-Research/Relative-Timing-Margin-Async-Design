How a mousetrap pipeline works

A mousetrap pipeline (Singh & Nowick, 2007) is a clock-less, latch-based asynchronous pipeline using bundled data: a bus of data wires travels with a single request wire, and the request is delayed so that it always arrives after the data on the bus has settled. Rather than a clock, each stage decides for itself when to capture, using one small gate and the request/acknowledge handshake with its neighbours.

One stage

  • A bank of latches holds the stage's data, and one more latch holds the stage's request (req_out). Their enable is shared.
  • That enable is generated by a single XNOR gate comparing this stage's request output with the request output of the next stage (which acts as the acknowledge).
  • When the two are equal, the XNOR output is 1 and the latches are transparent (open): the stage is empty and ready for new data.
  • When a new request arrives it flows straight through the open latch and req_out toggles. The two inputs of the XNOR now differ, its output falls and the latches become opaque - the data is "trapped", like a mousetrap snapping shut. This takes a short time, the mousetrap delay: request at latch D → through the latch → through the XNOR → enable low.
  • Once the next stage has taken the data, its own request toggles. It now equals this stage's req_out, the XNOR goes high again and this stage re-opens for the next item.

The timing rule that matters

Data and request leave the previous stage together. The request is slowed by a matched delay so it reaches the latch no earlier than the slowest data bit. Because the latch only closes a mousetrap delay after the request arrives, the data has until then to be stable at the latch input:

data delay  <=  request delay + mousetrap delay      (setup time ignored)

This is a relative timing constraint: it compares two delays on the same chip rather than a delay against a clock period, so it can be checked and its margin measured directly.

In this design

The generated pipeline module contains one stage under test. L1 latches launch the data and the request (opened by the synchronised ENABLE_L1). The data bits go through one delay line each; the request goes through a long buffer chain with four mux4 taps (selected by delay_ctrl). L2 latches capture the data. Their enable is enable_l2 = XNOR(req_out, last_l2_req), where last_l2_req is a latch (enabled by PRIME_L2) that plays the part of the next stage's acknowledge: priming it copies req_out into it, so the XNOR is 1 and L2 is open. When the request arrives req_out toggles and L2 closes. l2_fired = !enable_l2 then tells the scan chain that a capture has happened so it can load the results. The scan chain also provides all inputs and outputs (SI, SO, CLK, SE).

The experiment

Purpose. To measure how much relative timing margin a mousetrap stage really has on silicon: how much slower than the request the data can be before L2 closes without it. Buffer delays move with process, voltage and temperature, so the generator builds a ladder of data delays around each request delay and the chip tells us where the boundary falls.

Set-up. The request chain can be tapped at four points chosen with the 2-bit delay_ctrl (one request delay per target delay). For every target, a family of data delay lines is built whose delay is the target divided by (1 + p), with the offset p swept from +range to -range in steps of step (percent).

  • p > 0: the data delay is shorter than the request delay (data should win the race).
  • p = 0: data delay equals the request delay.
  • p < 0: the data delay is longer than the request delay (data should lose, apart from the mousetrap-delay allowance).

Procedure (one run, repeated for each of the four delay_ctrl values):

  1. Shift in, through SI with SE=1, a data word (one bit per delay line), the request bit and the delay_ctrl value.
  2. Reset and prime L2 (NRESET, PRIME_L2) so that L2 is open and last_l2_req matches req_out.
  3. Raise ENABLE_L1. It is synchronised to CLK by two flip-flops, then opens the L1 latches and releases every data bit and the request at the same instant.
  4. Each data bit travels down its own delay line; the request travels along the request chain to the selected tap and through the mux4.
  5. When the request reaches the L2 request latch, req_out toggles and, one mousetrap delay later, enable_l2 falls and L2 closes. Bits that arrived before this are captured; later bits are not.
  6. l2_fired goes high and, with SE=0, the scan chain loads {delay_ctrl, req_out, word_out}. Shift it out through SO.
  7. Compare the captured word with the word sent in: bit i correct means delay line i was fast enough for that request delay.

Result. For every target delay the pass/fail pattern across the delay lines (ordered by delay) shows where the boundary lies, and so the margin as a percentage of the request delay. setup/required_delays.tcl lists the intended delay of every line so the bit index in the scan data can be mapped back to a delay in picoseconds.

The sweep is a ratio, not an absolute amount, so one set of delay lines covers all four request delays: in compact mode each delay line has taps and its own mux4 (also selected by delay_ctrl) and is shared between all four targets.
