# OVERVIEW:
This is design to implement an experimental design to investigate the overhead required on the request delay of a bundled data system.

# Key IP blocks
* pipeline: A single mousetrap pipeline stage which consists of a programable request delay line (typically 4 values) and a number of delaylines which are tuned around the delays of the request.
The pipeline  config, request and data are setup by shifting it in to a scan chain which drives the L1 latch. The L2 latch is primed and then the L1 latch is made transparent. After the request has closed L2 the data stored in L2 is loaded in to the scan chain, and from there shifted back out to the tester.  Some of the data should have arrived to late to have been captured in L2 so, from looking at the results we will be able to pin the time to snap the latch within the bounds of 2 of the delaylines. Typically we would allow for +50% to -50% overhead on the request in steps of 5%.
* VE_block:  This instantiates a number of pipelines in to a single block and stitches the scan chains together- these could be instantiated as hard macros, firm macros (where we place the macros identically but allow routing based on the placement) or via some other method, such as setting placement regions or fully flat place and route.
* varExperiment: The top level design which include two VE_blocks connected together and attached to a set of  IO pins and some associated control logic. The two blocks can be located physically separately allowing a single set of pins to control both blocks. An alternative top level might take the hit on extra IO pins to save the potentially complex routing between the two blocks.

# Implementaion:
The design is written in a combination of SystemVerilog RTL and gate level Verilog. Some synthesis tools will optimise out RTL/primitive based buffer chains when elaborating design (even if told not too!), for this reason we implement using a physical cell, which the tools leave in place. The buffers/muxes associated with the delayline are included in the pipeline verilog via an \`include delays.v. This allows them to be changed to a different style without having to change the fundamental pipeline source which looks cleaner, but without having to add another level of hierarchy.  A python script is included which can be used to generate delays.v.  As this is a generic library we have used \`defines of LOGIC_* to define the gates The user must map LOGIC_* to appropriate cells from their technology libraries  - this should make changing technology relatively straight forward. In the repository these cells are set in the include file system_define so the mapping only needs to happen in one place - a set of technology agnostic functional cells are provided for simulation.
